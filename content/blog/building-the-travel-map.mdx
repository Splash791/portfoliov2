The Travel section went through two real implementations before landing
where it is now: a hand-rolled react-three-fiber globe with an optional
MapLibre flat-map view, then a rewrite onto the [globe.gl](https://github.com/vasturiano/globe.gl)
library with the map view dropped entirely. Here's the current shape, and
the bugs that shaped it.

## Why globe.gl, and why globe-only

globe.gl is purpose-built for exactly this — points, arcs, and a globe,
with a declarative-ish chained API over a managed three.js scene. It
replaced a hand-rolled react-three-fiber setup that was duplicating a lot
of what the library already does well: lat/lng-to-3D projection, arc
geometry, click handling on 3D points. The flat MapLibre map that used to
sit alongside it as the default view was removed outright — one
visualization, not two maintained in parallel.

The globe is still lazy — dynamically imported with `ssr: false` (it
touches `canvas`/WebGL at module-load time, so it can't run server-side
at all) and only mounted once the Travel section nears the viewport via
Framer Motion's `useInView` with a `200px` margin, so the chunk starts
loading before the section is fully on screen rather than after.

## WebGL still has a fallback

The WebGL capability check didn't go away just because the map did.
It's still a one-time `useSyncExternalStore` snapshot (try creating a
`webgl`/`experimental-webgl` context on a throwaway canvas; the result
can't change mid-session so there's no reason to re-check it) — if it
comes back false, the section renders a plain text fallback instead of
a broken canvas.

## Stylized first, real-earth later

The first globe.gl pass used a flat, abstract ink-colored sphere — no
real-earth texture, since the glass-and-gradient language around it
didn't obviously call for one, and it was the quicker thing to ship
first. It read as too flat and abstract next to everything else on the
page, so it was swapped for a true-color, day-lit Earth photo texture
plus a bump map for actual terrain relief (mountains and ridges catch
the light instead of a flat-shaded sphere). Both images are vendored
into `/public` (244KB + 378KB combined) rather than fetched from a CDN
at runtime, the same call made for the MapLibre worker fix earlier in
this project.

## Pins you can't see are pins that don't exist

Separately: on load, the globe showed zero pins. Not a rendering bug —
geometry and math. Three of the four trip stops (Tokyo, Canberra, Hanoi)
sit in the Eastern hemisphere, and with this camera setup a stop's
longitude alone decides whether it's front- or back-facing by default.
Most of the data was clustered on the far side of the sphere from the
starting camera angle, so a visitor landed on a bare globe and had to
manually orbit it to discover there was anything there at all.

The fix: set an explicit starting point of view (`globe.pointOfView({
lat: 10, lng: 120, altitude: 2.6 }, 0)` — `0` transition ms, so it's
immediate, not animated) that frames the cluster on load instead of
leaving it to chance. The altitude has since moved out a touch further
(from an initial `2.2`) to leave visible padding around the sphere
instead of it nearly touching the container edges. Each pin's hit
radius was also bumped up separately (`pointRadius(0.9)`, up from
`0.4`) — in globe.gl, that one value drives both the rendered marker
size and its raycast click area together, so a bigger pin is also a
bigger, easier target.

## Reduced motion, done per-feature rather than as one switch

The globe has three independent things that move, and reduced motion
gates each one separately rather than toggling the whole scene on or
off: continuous auto-rotation (`controls.autoRotate`) is skipped
entirely when reduced motion is on, not just slowed down; route arcs
switch from a continuously flowing dash animation
(`arcDashAnimateTime`) to fully-formed static lines
(`arcDashLength(1)`, `arcDashGap(0)`); user-driven orbit (drag-to-rotate)
stays enabled either way, since manually dragging the globe isn't the
kind of motion reduced-motion settings are about. Zoom is the one
exception that isn't a reduced-motion decision at all — `controls.
enableZoom = false` is set unconditionally, after two separate rounds of
the sphere clipping past its own container at different zoom levels.
Tuning a safe zoom range twice and having it break again wasn't worth a
third attempt; removing zoom outright removed the whole failure class.

## Opening a trip

Clicking a pin calls the same `onSelectTrip` callback regardless of
which pin it is, which opens a gallery panel reusing the exact
focus-trap / Escape / click-outside-to-close pattern already built for
the project modals — one shared interaction model, not a second one
invented for the globe.

## A pin with no visible affordance is a pin nobody finds

Even with the camera framed correctly, clicking a pin was never
actually *discoverable*. The only signal that a pin was interactive at
all was `onPointHover` swapping the cursor to a pointer — a real
affordance on a desktop mouse, and no affordance whatsoever on a touch
screen, where there's no hover state to swap, and no signal at all for
a keyboard-only or screen-reader user, since `onPointClick` is wired
only to globe.gl's internal mouse-raycast against the canvas.

The fix didn't touch the globe at all: a plain instruction line plus a
row of real `<button>` elements — one per trip, each carrying a small
dot in that trip's pin color — now sits below the globe, calling the
exact same `onSelectTrip` the pins call. Same destination, three more
ways to get there: it's keyboard-focusable, it works identically on
touch, and it even works when WebGL isn't available at all, since
nothing about it depends on the canvas rendering.
